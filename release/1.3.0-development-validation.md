| Entry | Code | Read/write and ownership |
| --- | --- | --- |
| snapshot | queue.ts snapshot → evaluateReadiness | Read-only committed snapshot, reject dirty execution configuration |
| draft | queue.ts draft | Recheck during queue transaction before sealing; preserve prior drafts on failure |
| review | queue.ts reviewDraft, tools.ts, presentation.ts | Evidence sidecar bound to draft digest; complete bounded question and paginated evidence |
| enqueue | queue.ts enqueue, tools.ts, approvals.ts | Current readiness under queue lock; publish item/proof together, consume receipt afterward |
| reserve | queue.ts reserve | Shared Git scan outside transaction, compare queue revision before reservation; persist wait without a worker |

| restart/reconcile | queue.ts constructor/reconcile, service.ts | Validate waiting bindings; preserve original approval and baseline; reconcile real worker exit |
| upgrade | lifecycle.ts assertQueueIdle | No active worker or retained workspace; waiting-only inbox may survive upgrade |
| process ownership | storage.ts, process-ownership.ts | C locale capture; unknown old localized identity fails closed; no inferred lock recovery |

The queue schema remains 1 with additive startup evidence. Existing contract digests
exclude only the new mutable `precondition` field; their baseline rules and validation
scope do not change. A version older than 1.3.0 cannot resume the new waiting state.

## Result model and fingerprint (PC-002)

`Readiness` carries version, readiness state, reason code, planning/observed/target
HEAD, typed paths (including rename source and destination), ownership, next action,
committed/installed versions, check time and original approval digest. The fingerprint
covers all condition fields except check time. It omits contents of the exempt prefix
file. Prefix validation remains independent. The result declares no coding/workspace
only for the startup path; existing workspaces never enter this state.

## Approval publication protocol (PC-010)

The live ledger validates a receipt with `peek`, then enqueue validates the exact
sealed draft and current readiness in the queue transaction. Item and proof are
published in one atomic, fsynced queue document. Only successful publication consumes
the in-memory receipt. Check/write failure leaves the live receipt available. A crash
before publication loses it and requires a fresh human question. A crash after
publication is handled by idempotent exact-key/digest/phrase replay. No receipt can
approve a different draft or manufacture a second task. The draft remains editable
through a new version on any pre-publication failure.
