OpenCode · Orchestrated Workflow V2

从一句需求，到人工验收后回到原分支

这是一份可以逐行照抄的操作手册。正常流程中，你只需在 Terminal 做环境准备并启动一次 OpenCode，之后始终留在同一个 scheduled-planner 会话里，用 /change 输入一句话需求，再通过三张 OpenCode 单选卡完成确认；方案、合同和成果三次确认都只需点击审批选项。 worktree、任务分支、Coder、Reviewer、质量门、提交、回原分支以及成功后的任务分支删除都由系统接管。

1 个入口 opencode --agent scheduled-planner .
3 次人工确认 方案确认、合同确认、最终验收，各自有明确边界。
0 次手工编排 不用手动创建 worktree、排队、启动 Coder/Reviewer 或合并。

点击批准会触发的完整自动链路

1. 封存计划和合同但暂不提交 记录原分支、原 HEAD 与文件哈希；规划文件留在任务 diff 中等待最终合并提交。
2. 原地切换事务任务分支 取得持久仓库租约后，在当前工程目录创建任务分支，不复制工程；仅显式配置隔离模式时创建一个 worktree。
3. 受限 Coder 通过 TDD 编码 只能改合同允许路径，记录基线、真实 RED 和后续质量门证据。
4. 新会话 Reviewer 独立复核 Reviewer 只读检查合同、diff、测试和证据；配置只允许一次受控修复循环。
5. 封存 diff 与验收包 通过后记录 diff SHA、文件列表、验收条件和 Reviewer 结论。
6. 主动停下等待你 进入 AWAITING_HUMAN，代码、测试、计划和合同此时都尚未提交。
APPROVED_CONTRACT→ PREPARING→ PENDING→ CODING→ READY_FOR_REVIEW→ REVIEWING→ AWAITING_HUMAN

系统随后自动完成

  1. 重新核对状态、原分支、合同 SHA、sealed diff SHA 和 Reviewer 的 APPROVED 结论。
  2. 把合同允许的产品文件与封存的计划、任务合同合并成唯一任务提交。
  3. 确认任务基线到候选 HEAD 恰好只有这一个提交，并在当前任务目录验证，不创建第二个候选 worktree。
  4. 重新执行聚焦测试、完整单测、构建、lint，以及合同要求的设备测试。
  5. 只有验证全部通过且原分支未漂移，才把记录的原分支快进到已验证候选提交。
  6. 清理或分离可选任务 worktree，再安全删除已经合入原分支的本地任务分支。
  7. 记录分支删除证据并把状态写为 COMPLETED；失败或阻塞时保留任务分支用于恢复。

故障处理：先看状态和证据，不要绕过门禁

硬停止是保护机制。它的目标是让失败可解释、原分支不受污染，而不是逼你手工补跑整套流程。

现象或状态 含义 你应该输入什么 不要做什么
ANDROID_HOME is not set 启动 OpenCode 的 Terminal 没继承 Android SDK 环境。 source ~/.zshrc；若仍为空，执行第 1 步两条 export，再从同一窗口重启 OpenCode。 不要创建 local.properties；不要给 Gradle 命令临时加环境前缀。
Git worktree is dirty 原工作区存在未提交或未跟踪修改，无法可靠封存基线。 输入 git status --short 和 git diff，只提交确认属于当前分支的文件，或有意识地暂存它们。 不要盲目 reset --hard、clean 或提交所有文件。
找不到 /change / Planner / Skill OpenCode 没正确发现仓库配置、项目命令、固定插件、Agent 或 Skill。 确认 .opencode/commands/change.md 存在，再运行 opencode debug config、opencode debug agent scheduled-planner、opencode debug skill 和 ./scripts/automation/preflight.sh --source。 不要跳过预检后直接调用 Coder。
BLOCKED，原因为 reviewer exited without submitting a decision Reviewer 会话在写入结论前耗尽步骤预算；已完成代码和封存证据仍可直接复用。 在 OpenCode 输入 /resume-review TASK-ID；脚本验证 sealed diff 后只重启 Reviewer。 不要改成 PENDING，不要重跑 Coder，也不要 reset 已封存的 worktree。
BLOCKED 前置条件、范围、权限或工作区准备失败。 运行 ./scripts/automation/status.sh TASK-CHONGQING-CITY，按 evidenceDirectory 查看具体日志，并在 OpenCode 说明阻塞原因。 不要手工建 worktree、改状态 JSON 或重复排队。
TEST_FAILED 真实 RED 之后的实现或某个质量门仍未通过。 让 Planner 展示失败测试与日志；若需扩大路径或目标，生成新合同或新任务。 不要伪造 RED、删测试或跳过质量门。
NEEDS_HUMAN Reviewer 不批准，且允许的自动修复循环已经用完或不适用。 查看 review.json 和修复建议，决定是否用新的任务合同继续。 不要把它当作 AWAITING_HUMAN 输入验收通过。
INTEGRATION_BLOCKED 候选集成冲突、复验失败或原分支在验证期间发生漂移；原分支不会被错误推进。 查看 integration-verification.log 和 integration-failure.json，在 OpenCode 明确选择恢复或新任务。 不要自动解冲突、强推或手工改 sealed diff。
sealed diff changed 人工验收对象与当前任务工作区不再一致。 停止验收，让系统重新审查并产生新的封存证据。 不要继续输入第三条确认语。

正常流程中，这些命令不要手工执行

它们不是“少一步也能跑”的快捷方式，而是会绕开合同哈希、状态机、权限隔离或最终验证。

git worktree add ...
worktree 路径、分支、基线与共享状态必须由脚本共同记录。
./scripts/automation/queue-task.sh ...
V2 编排路径由 Planner 直接推进，不需要人工排队。
opencode run --agent scheduled-coder ...
Coder 必须在合同绑定的专用 worktree 中由编排器启动。
opencode run --agent scheduled-reviewer ...
Reviewer 必须在新会话中读取封存 diff 和完整证据。
git add / commit / merge / cherry-pick
合同提交、产品提交和候选集成都由确定性脚本负责。
git push（自动链路内部）
验收只授权本地集成；远端 push 是完成后单独做出的决定。
也不需要创建 OpenCode Scheduler 定时任务。automation/scheduler/ 下的提示词只保留作兼容诊断； 当前 V3 的启动入口始终是 scheduled-planner 会话，会话内的需求入口是 /change。

最终速查：到底在哪儿输入

如果只记一张表，就记这张。带“自动”的行只是系统行为，不需要复制。

顺序 位置 你的核心操作 完成标志
1 Terminal 加载 ANDROID_HOME，运行 preflight，启动 scheduled-planner。 进入 OpenCode 会话。
2 OpenCode /change <一句话行为需求>；如有必要，回答 Planner 的少量澄清问题。 看到完整、可接受的方案。
3 OpenCode 在“方案确认”中点击 批准方案，生成计划和任务合同。 CONTRACT_REVIEW。
4 自动 人工检查 无需输入；阅读 Planner 自动展示的复核卡。 确认合同可执行且未越界，并看到确认选项。
5 点击确认 点击 合同已复核，批准自动执行到人工验收阶段。 进入 APPROVED_CONTRACT 并启动自动链路。
6 自动 系统取得租约并原地切换任务分支，运行 Coder、质量门、Reviewer，生成验收包并主动弹出复核卡。 sealed diff 与 Review 均已封存，卡片停在 AWAITING_HUMAN。
7 自动展示 人工检查 无需输入；按复核卡依次检查 P0 行为、回归/范围，再看 P1 证据、绑定与剩余风险。 你能明确判断通过或不通过。
8 点击确认 点击 验收通过，提交到原分支。；不通过或未完成检查则选择对应选项。 COMPLETED，本地原分支已更新，已集成的任务分支已删除。
9 Terminal 查看分支、状态和提交；如需远端同步，再显式执行 git push。 本地完成；可选远端完成。
