Operating Model

正常路径只保留三个必要人工关口

人工负责需求含义、合同授权和最终风险接受；机械操作与重复验证全部交给可审计的自动化。

01
人工关口 1

批准方案

Planner 先展示范围、验收条件、测试与非目标，再弹出“方案确认”单选；用户点击批准后才生成计划和任务合同。

人工关口 2

批准合同并执行

人工复核生成的 Markdown 计划和 JSON 合同，在“合同复核”单选中点击批准后，自动编排持续运行到人工验收。

人工关口 3

验收并提交原分支

Reviewer 通过后停在 AWAITING_HUMAN。用户在“成果验收”单选中点击通过，集成器才更新原分支并删除已集成的本地任务分支。

原分支锚定

不硬编码 main

合同批准时记录当前原分支和 HEAD；最终只能集成回这条分支。

中段全自动

不再手敲十一组命令

任务分支、仓库租约、Coder、Reviewer、状态检查和证据汇总由编排器连续完成。

职责隔离

模型不直接操作 Git 集成

Coder 只改合同允许文件；Reviewer 只读；提交与集成仅由确定性脚本执行。

交付边界

默认只提交，不自动 push

完成状态表示本地原分支已有单一任务提交。远端 push 仍需单独、明确授权。

自动化不等于放宽门禁：原工作目录不干净、合同含糊、环境缺失、测试失败、审查不通过或原分支漂移时， 编排器必须停止并保留证据；正常路径不需要人工接力，异常路径不能静默猜测。

确认方案，自动生成计划和任务合同

Planner 应先展示任务 ID、验收条件、允许路径、目标测试、非目标和设备测试策略，但此时不写文件。

确认无误后，在 Planner 自动弹出的“方案确认”单选框中点击一项：

● 批准方案，生成计划和任务合同。
  确认当前方案并生成两份待复核的规划文件。

○ 需要调整方案
  不生成文件；随后说明要调整的目标、范围或验证方式。
Planner 生成 docs/plans/<TASK-ID>.md 与 automation/tasks/<TASK-ID>.json，运行合同校验，并进入 CONTRACT_REVIEW。只有点击第一项才会生成文件；直接发送同名文本不构成批准。 生成文件只做哈希封存，暂不提交；生成文件不等于授权执行。

人工复核合同，并用一次确认启动自动执行

OpenCode 必须展示计划全文、合同关键字段、校验结论和将要记录的原分支。人工至少确认：

  • 输入为 查看重庆的记录列表。
  • userGoal == BrowsePersonalInfoList。
  • slots.city == "重庆"。
  • allowedPaths 只有实现文件和对应测试文件。
  • 先 RED 后最小实现，已有城市行为不变。
  • 不改 UI、导航、依赖、Gradle、远端解析或意图优先级。
  • 原分支是当前实际分支，例如 feature-opencode-scheduler，而不是硬编码的 main。

复核完成后，在 Planner 自动弹出的“合同复核”单选框中点击一项：

● 合同已复核，批准自动执行到人工验收阶段。
  确认当前封存内容并自动执行到人工验收。

○ 需要调整计划或任务合同
  保持停止状态，并说明需要修改的内容。
只有点击第一项才生成一次性执行授权，直接发送审批文本无效。此后编排器自动推进，直到成功进入 AWAITING_HUMAN，或因硬门禁进入失败状态。批准合同本身不会产生 Git 提交。

编排器原地准备事务分支、编码并审查

从这一阶段开始，用户不再执行 Terminal 命令。编排器依次完成：

  • 建立基线：记录原分支、未改变的原 HEAD 与合同 SHA；计划和合同继续保持未提交。
  • 准备环境：取得持久仓库租约，在当前工程目录创建并切换唯一任务分支，不复制源码。
  • 可选隔离：只有将 workspaceStrategy 显式设为 isolatedWorktree 时才创建一个任务 worktree。
  • 运行时配置：把任务根路径、分支和租约写入 Git 公共状态区，而不是提交单次激活配置。
  • G0：新增测试前，全量 testDebugUnitTest 必须通过。
  • G1：先添加重庆聚焦测试，获得真实 RED 并记录证据。
  • G2–G6：完成最小实现、单测、构建、Lint、设备测试策略和范围门禁。
  • 范围计数：计划和合同必须保持封存哈希不变，但不占用 maxChangedFiles；该上限只统计产品代码、测试及其他合同授权文件。
  • G7：自动启动全新的只读 Reviewer，复跑验证并核对封存 diff。
# 编排器内部流水线；不是人工命令
PREPARING → PENDING → CODING → READY_FOR_REVIEW
→ REVIEWING → AWAITING_HUMAN
Coder 仍然不能创建 worktree、提交、merge、rebase 或 push；这些能力只授予带状态校验的确定性编排脚本。

在 OpenCode 中完成集中式人工验收

自动阶段成功后，OpenCode 一次性展示验收包，而不是要求人工逐个查状态文件。验收包必须包含：

  • 业务行为、最终产品 diff 和允许路径对照。
  • 将随产品变更一并进入同一提交的计划与任务合同路径。
  • G0 基线、真实 RED、聚焦测试、全量单测、构建与 Lint 结论。
  • Reviewer 决策、验证退出码、封存 diff SHA 与剩余风险。
  • 即将更新的原分支、当前 HEAD、预计单一任务提交信息，以及是否发生分支漂移。

检查完成后，在 Planner 自动弹出的“成果验收”单选框中点击一项：

● 验收通过，提交到原分支。
  确认当前 sealed diff，并开始经过复验的本地集成。

○ 验收不通过，需要说明失败项
  保持封存，不集成；随后说明失败条件。

○ 暂不决定，保持封存
  不改变状态，稍后可重新打开同一张验收卡。
只有点击第一项才构成验收；直接发送同名文本无效。该选择只对当前任务 ID、当前封存 diff SHA 和已展示的原分支有效；任一值变化都必须重新展示并选择。

集成器自动提交到原分支并回报结果

最终确认后，确定性集成器自动完成以下操作：

  • 再次验证 AWAITING_HUMAN、Review 批准、diff SHA、合同范围与原分支身份。
  • 将合同允许的代码/测试与已封存的计划/合同一起暂存，在任务分支生成一个提交。
  • 确认从任务开始基线到候选 HEAD 恰好只有这一个提交，并在当前任务目录复跑确定性验证，不建立第二个候选目录。
  • 原分支仍等于批准基线时执行快进；只要发生漂移就进入 INTEGRATION_BLOCKED，不自动 cherry-pick。
  • 原分支安全到达已验证提交后，清理或分离可选任务 worktree，并用安全删除移除本地任务分支。
  • 保存集成与分支删除证据、释放持久租约，最后进入 COMPLETED；失败或阻塞时保留任务分支。
state=COMPLETED
originalBranch=feature-opencode-scheduler
productCommit=<COMMIT>
verificationExitCode=0
taskBranchDeleted=true
pushed=false
“提交到原分支”是本地 Git 提交，不等于 push。只有用户另外明确说“推送到远端”时，才允许执行网络写入。
Implementation Contract

这套自动流程已经落地的能力

以下能力已由仓库内 Agent、Skill、配置和可测试的确定性脚本实现，不依赖提示词临时模拟关键 Git 或状态操作。

04

受控 Orchestrator

scheduled-planner 加载专用 Orchestrator Skill。它不能编辑产品代码，只能调用白名单事务脚本、启动隔离的 Coder/Reviewer，并向用户展示审批内容。

两条主事务与一条安全中止接口

./scripts/automation/approve-and-run.sh <TASK-ID> <APPROVAL-TOKEN>
./scripts/automation/accept-and-integrate.sh <TASK-ID> <ACCEPTANCE-TOKEN>
./scripts/automation/abort-task.sh <TASK-ID> <ABORT-TOKEN>

第一条负责基线、事务分支、租约和自动流水线；第二条负责封存校验、同目录复验和原分支快进；第三条归档现场并恢复原分支。

非跟踪运行时配置

任务根路径、持久仓库租约和运行状态存放在 Git common dir。不得通过修改并提交本机绝对路径激活单次任务。

幂等、锁和可恢复状态

同一仓库只允许一个编排任务持有租约；重复确认不得重复建分支、重复提交或重复集成。租约跨人工等待保留，进程中断后从证据状态恢复。

角色 允许能力 明确禁止
Planner 读取仓库；在首次批准后生成计划与合同；按后续确认调用白名单事务脚本 直接编辑产品、直接执行 Git 变更或 push
Orchestrator 校验批准令牌、管理状态/持久租约/事务任务根、启动隔离 Agent 自行解释需求或编辑产品代码
Coder 只编辑合同 allowedPaths，执行 TDD 和 G0–G6 任何 worktree、commit、merge、rebase、push 和合同修改
Reviewer 全新只读上下文，复验并提交结构化决定 编辑任何仓库文件或继续复用 Coder 会话
Integrator 最终批准后将允许文件与封存计划/合同合为一个提交、验证候选并更新原分支 跳过 SHA/范围校验、自动解冲突、force push 或修改未授权分支

Failure Handling

异常才需要人工介入，旧批准不会被复用

编排器允许合同内的有界自动修复；环境、歧义、超限失败和 Git 冲突仍必须停止。

07
状态 常见原因 正确处理
CONTRACT_INVALID 合同缺字段、范围含糊、原分支无法确定或审批对象已改变。 保持在合同复核阶段，由 Planner 修订；绝不取得执行租约或切换任务分支。
BLOCKED SDK、依赖、基线、权限、仓库租约或任务根身份不满足硬门禁。 保留日志并报告一条可执行的修复建议；修复后从最近安全状态恢复。
TEST_FAILED 聚焦测试、全量单测、构建或 Lint 在允许修复次数后仍失败。 自动修复次数耗尽后转 NEEDS_HUMAN，不得无限消耗模型时间。
CHANGES_REQUESTED Reviewer 发现语义、测试质量或 diff SHA 不一致。 合同内且未超限时自动返回 Coder，并启动新的 Reviewer；否则交还人工。
INTEGRATION_BLOCKED 原分支偏离任务开始基线、任务根身份改变或单一任务提交复验失败。 原分支保持不变，不自动 cherry-pick；保留任务分支、租约与证据，等待人工决定。
ABORTED 人工明确决定终止一个已停止的任务。 有产品修改时与计划/合同合为一个 recovery commit；仅有规划文件时只归档 diff、不提交；随后恢复原分支并释放租约。

问题解决后，Planner 必须根据保留的证据重新校验最近安全状态；如果合同、diff、原分支或 HEAD 已变化，必须回到相应人工批准关口，不能沿用旧批准继续执行。

自动化不得使用 --dangerously-skip-permissions、force push、自动解决 Git 冲突、修改未授权分支， 也不得把失败当作继续猜测的理由。最终接受令牌只能使用一次，并且必须绑定任务 ID、diff SHA 与原分支 HEAD。
