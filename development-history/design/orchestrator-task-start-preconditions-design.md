# 任务启动前置条件检查与等待机制方案

日期：2026-10-11。

状态：1.3.0 开发及产物验证已完成（2026-10-12），已同步产品仓库并提交、
推送 GitHub `main`（`ec31c8e`）；npm `1.3.0` 已发布并核验，未升级实际 WordPress。完整回归及修复后复验分别记录于
[完成记录](../../../../program/cctest/taskdescriptions/orchestrator-1.3.0-preconditions/completion.md)。第 8 节任务逐项证据见该记录。本文记录“避免已入队、尚未开始编码就被阻塞”的方案，
并纳入用户明确要求：**`automation/automation-commit-prefix` 文件有修改，不算工作区不干净。**

## 1. 背景与目标

WordPress 升级至插件 1.2.3 后，两个任务在升级文件尚未提交时入队。
Planner 仍从旧提交读取配置；后台执行器在创建任务工作区前发现未提交改动，
将任务标为 `BLOCKED`，且失败检查没有输出文字，最终错误原因为空。

已通过临时 Git 环境复现：旧基线加升级后的工作树产生 14 个变更，干净工作区
检查失败；以升级提交作为基线，同一工作树检查通过。完整证据见
[WordPress 1.2.3 启动诊断](../../../../program/cctest/taskdescriptions/wordpress-1.2.3-start-diagnosis/diagnosis.md)。

目标是“审批前检查 + 执行前复查 + 条件等待”：

- 提前识别未提交的插件升级、配置变更与其他执行前置条件。
- 保留前一个受控任务执行期间继续规划、审批和排队后续任务的能力。
- 将暂时不能启动与真正的编码、测试失败分开，不消耗模型或实现修复预算。
- 任何等待或失败都提供具体原因和可执行的下一步。
- 不自动提交用户文件，不静默改变已批准合同、规划基线或验证范围。

## 2. 工作区脏文件判定及提交前缀例外

规划前检查、审批卡、入队复核和执行前复查必须使用一致的路径分类规则，避免
一个入口认为可执行、另一个入口却认为工作区不干净。

### 2.1 明确排除 automation-commit-prefix

标准仓库相对路径为 `automation/automation-commit-prefix`。该文件是用户维护的
提交前缀配置，其修改不得计入工作区脏文件集合，具体要求如下：

- 无论修改尚未暂存还是已经暂存，都不能因此拒绝规划、审批、入队或任务启动。
- 不因该文件修改进入 `WORKTREE_DIRTY`、`WAITING_PRECONDITION` 或重新审批流程。
- 必须先处理此精确路径例外，再匹配 `automation/**` 等宽泛保护路径。
- 新增的启动准备状态、执行配置漂移判断及相应检查指纹不能把其内容变化重新
  包装成升级漂移或前置条件变化；不能只在 Git 状态展示层隐藏它。
- 若它与其他文件同时修改，仍检查并报告其他文件；不能因此放行整个工作区。
- 不将该例外扩展为任意目录下所有同名文件，也不扩展到整个 `automation/`。
- 保留现有提交前缀读取和独立格式校验。无效内容应报告提交前缀配置错误，
  不能误报为工作区不干净；本方案不改变其内容规则或自动提交归属。

上述例外针对文件改动判定，不意味着可以改写旧合同摘要或绕过既有 HEAD、
规划输入和授权校验。涉及已经发生的 Git 提交时，仍遵守合同原有的基线策略。

### 2.2 其他路径

延续现有 `.automation-worktree-allowlist` 的受控例外语义，不新增长期忽略整个
配置目录的规则。新增、暂存、未暂存、删除及重命名均纳入分类；重命名要检查
源路径和目标路径，不能借前缀文件例外隐藏对其他文件的修改。

区分三类实际变更：

1. 插件安装、执行配置、合同模板和验证脚本等受保护文件的未提交变更。
2. 可证明属于当前受控任务、且与其工作区所有权一致的变更。
3. 无法归属于当前受控任务的其他变更。

仅凭后台存在一个任务，不能把所有工作区改动都归类为受控任务变更。

## 3. 规划前检查

固定规划快照前，检查受保护文件是否存在影响执行的未提交变更，例如
`opencode.json`、`automation/config.json`、任务模板及验证脚本。
此检查必须先排除第 2 节的提交前缀例外。

发现插件升级或配置变更尚未提交时，展示文件列表、当前已提交配置与已安装
版本的区别，暂不生成可审批合同。例如：

> 检测到插件升级改动尚未提交：当前已提交配置为 1.2.1，工作区安装版本为
> 1.2.3。请先审阅并提交升级改动，再生成任务合同。

版本相同也可能有配置漂移，因此不能仅比较版本字符串。这里不替用户执行
Git 提交、回退或清理。问题处理后重新获取规划快照，避免继续使用旧配置生成合同。

## 4. 审批卡与入队复核

审批卡新增执行准备状态、检查时间、规划 HEAD、受影响文件和下一步操作。
检查结果绑定当前草案；入队时重新核验，不能把较早展示的检查结果当成永久有效。

| 当前情况 | 行为 |
| --- | --- |
| 工作区符合例外规则、配置与规划基线一致 | 允许入队 |
| 仅提交前缀文件有修改 | 按正常准备状态处理，不能判为脏工作区 |
| 前一个受控任务正在占用工作区 | 允许排队，显示等待前序任务释放工作区；沿用合同的依赖及基线策略 |
| 存在无法归属的其他未提交改动 | 保留草案，提示处理具体文件后重新检查；本次不入队 |
| 插件、执行配置或相关规划输入已变化 | 要求重新规划和审批，不能复用失效的复核卡 |

前置条件不满足时，不产生一次已批准执行，也不应出现“审批已使用但没有任务”的
半完成状态。审批凭据、草案绑定与队列写入需要保持一致；草案发生变化则重新复核。

不采用“一有未提交改动就禁止所有入队”的规则，以保留连续任务排队能力。

## 5. 执行前复查与条件等待

入队后、实际创建任务工作区前再次检查。两者之间仍可能发生外部修改，不能
因为已经审批就省略复查。

新增拟议状态 `WAITING_PRECONDITION`，专门表示尚未开始编码且启动条件暂未满足。
每个等待项保存原因码、文件列表、检查时间、基线与审批绑定、恢复要求。

示例：

> 等待工作区恢复干净：发现 3 个未提交文件。尚未调用 Coder，未消耗修复次数。

等待行为要求：

- 不创建编码工作区，不调用模型，不启动 Gradle，不消耗实现修复次数。
- 不长期占用唯一执行槽；共享目录本身不满足条件时，也不能让其他任务绕过检查。
- 使用现有事件唤醒及受控周期扫描重新检查，不依赖模型轮询，通知应去重。
- 暂停时不自动开始普通任务；取消后不能因条件恢复重新执行。
- 重启服务后保留等待原因、原始审批和基线，不重新制造执行批准。

条件恢复后的处理：

| 复查结果 | 下一步 |
| --- | --- |
| 工作区恢复可用，合同与基线仍有效 | 自动重新参与调度 |
| 前序任务完成，且原合同明确允许对应基线刷新 | 按既有授权验证后继续 |
| 用户新提交改变执行配置或相关规划输入 | 转为等待重新规划、审批 |
| 原合同不允许基线刷新 | 保留原审批记录，要求按现有规则处理，不自动换 HEAD |

`WAITING_PRECONDITION` 是新的拟议状态。落地时须同步处理持久化、状态展示、
调度器、取消入口、恢复流程与兼容性；不能只改状态字符串，也不能把已经开始
执行的失败任务直接归入此状态。

## 6. 错误证据与服务状态

每次检查失败至少包含：

- 检查名称和原因码，如 `WORKTREE_DIRTY`、`EXECUTION_CONFIG_CHANGED`。
- 具体文件路径及变更类型；排除提交前缀文件等有效例外。
- 命令退出码、信号或启动错误，以及安全且限长的诊断输出。
- 是否已开始编码、是否产生工作区、用户可以采取的操作。

即使子进程 stdout/stderr 都为空，也必须生成兜底信息，禁止将空字符串作为
用户唯一可见的失败原因。完整路径列表可通过现有证据分页提供，审批卡保留摘要。

本次故障应能够显示：

> WORKTREE_DIRTY：14 个插件升级文件尚未提交，任务未开始执行。
> 请审阅并提交升级改动后重新规划。

同时修复已确认的进程身份区域设置问题：统一进程启动时间的采集格式，使服务
启动和查询采用相同规则，避免中英文日期串导致存活服务被判为离线。不能因
格式不匹配就删除锁、重复启动服务或接管活动任务。

## 7. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 插件升级文件未提交即开始规划 | 展示升级文件及处理方法，不生成可审批合同 |
| 仅 automation/automation-commit-prefix 未暂存修改 | 不判为脏工作区，正常规划、审批和启动 |
| 仅提交前缀修改已暂存 | 同上，不因暂存状态改变例外 |
| 提交前缀与真实受保护配置同时修改 | 仅报告真实配置变更，不能放行或归罪于提交前缀 |
| 提交前缀位于 automation/** 保护规则下 | 精确例外优先，不触发配置漂移或启动指纹失效 |
| 提交前缀内容不符合既有格式规则 | 报独立配置错误，不报 WORKTREE_DIRTY |
| 前一个受控任务正常执行 | 后续任务仍可规划和排队，显示等待原因 |
| 展示审批卡后新增外部改动 | 入队复核发现变化，草案保留且无半完成批准 |
| 入队后、执行前出现外部改动 | 进入前置条件等待，未调用模型、未消耗修复预算 |
| 外部改动消失且原批准仍有效 | 自动恢复调度，不重复入队 |
| 等待期间提交了影响配置或规划输入的新代码 | 要求重新规划审批，不静默更新旧合同 |
| 等待期间取消或暂停 | 遵守取消、暂停语义，不能自行开始任务 |
| 子进程非零退出且没有错误输出 | 展示检查名称、退出状态及可处理的原因 |
| 服务重启或中英文 locale 不同 | 等待状态持久、服务存活判定一致、不错误接管锁 |

交付前应在隔离夹具中重现本次 WordPress 的升级未提交场景，并验证清晰提示、
取消、新基线重新规划与执行的完整流程。实际 WordPress 队列状态的修改和插件
升级不属于仅记录本方案的操作。

### 8.1 检查模型与统一路径规则

- [x] **PC-001：梳理检查入口和状态消费者。**
  逐项列出 snapshot、draft、review、enqueue、reserve、Worker prepare、status、
  cancel、resume、服务重启和升级检查的调用位置，检查持久化状态与终态判断。
  主要检查 `src/queue/`、Shell 模板和对应测试。
  交付：入口对照表，标明读写行为、锁边界及旧合同兼容点。依赖：无。

- [x] **PC-002：定义前置条件检查结果。**
  统一准备状态、原因码、路径及变更类型、检查时间、规划 HEAD、观察到的 HEAD、
  所有权结论与下一步操作；定义哪些字段参与条件指纹，哪些仅用于展示。
  时间戳不得使同一条件持续产生新通知；等待证据不能改变原批准摘要。
  验收：各入口能消费同一种结果，异常和无法确认的情况有明确表示。依赖：PC-001。

- [x] **PC-003：实现 Git 变更采集。**
  采集已暂存、未暂存、未跟踪、删除和重命名，使用可正确处理空格、中文、换行
  文件名的路径格式；重命名保留源、目标两端；沿用已有有效忽略规则。
  验收：路径及变更类型完整，没有因输出截断或解析错误把脏工作区判为干净。
  依赖：PC-002。

- [x] **PC-004：统一提交前缀文件例外。**
  在 TS 和 Shell 共用的判定规则中，优先排除精确路径
  `automation/automation-commit-prefix`，随后才处理 `automation/**` 等保护模式。
  将例外贯穿脏路径、配置漂移及新增条件指纹计算；保留独立前缀格式校验。
  验收：仅暂存或未暂存的前缀修改都不触发等待、拒绝或重新审批；混合变更仍能
  识别其他问题文件。依赖：PC-003。

- [x] **PC-005：区分任务占用与外部改动。**
  联合队列 active、工作区元数据、租约、任务范围和已有执行证据确认变更归属。
  仅路径位于 allowedPaths、或仅有一个活动任务，不足以证明全部改动归属。
  验收：前序受控任务不阻断正常排队，混入无法确认归属的变更仍有明确处理结果。
  依赖：PC-004。

- [x] **PC-006：实现只读准备状态评估器。**
  组合路径分类、当前分支、已提交与实际执行配置、安装状态和任务所有权，输出
  PC-002 定义的结果；版本相同但配置内容变化也能被识别。
  检查不得修改工作树、合同或队列，不运行 Gradle、模型或 Git 提交。
  验收：同一现场多次检查结果一致，除展示时间外不制造条件变化。依赖：PC-005。

### 8.2 规划、审批和入队

- [x] **PC-007：接入规划前升级检查。**
  在生成可审批规划前检查受保护文件，发现升级未提交时显示实际文件和处理步骤，
  并区分“已安装版本”与“提交中的配置版本”；避免继续把旧快照描述为新版本配置。
  验收：复现升级未提交时不能生成可审批合同；仅提交前缀修改时正常通过。
  依赖：PC-006。

- [x] **PC-008：接入草案封存前复查。**
  在 draft 入口校验规划期间配置和相关输入是否变化，不只依赖 Planner 提示词。
  保留可继续编辑的需求或草案，明确何时必须重新获取 snapshot。
  验收：绕过界面直接调用草案入口也不能封存已失效的规划。依赖：PC-007。

- [x] **PC-009：扩展审批复核卡。**
  在 `src/queue/presentation.ts`、工具响应及 CLI 展示中加入准备状态、检查时间、
  基线、文件数量和下一步；大列表走现有证据分页，完整审批问题必须保留。
  验收：可执行、等待前序任务、需处理外部改动、需重新规划四类状态可区分，
  提交前缀修改不作为阻塞原因出现。依赖：PC-008。

- [x] **PC-010：定义审批凭据与入队的一致性处理。**
  梳理 `src/queue/approvals.ts`、tools 和 queue 的检查、消费凭据、写入队列顺序。
  明确复查失败、写入失败、重复请求和进程中断时的结果；不复用已消费凭据，也
  不产生“批准已消耗但没有可追溯任务或失败结果”的半完成状态。
  验收：形成事务或可恢复协议及对应故障注入用例。依赖：PC-001、PC-002。

- [x] **PC-011：接入入队时最终复核。**
  在 enqueue 时重查准备状态和草案绑定，落实 PC-010 的一致性处理。
  草案未变但当前条件不满足时保留草案并返回原因；草案或配置已变则要求新复核。
  验收：审批卡展示后新增文件能被发现；前序任务占用仍允许排队；重复提交不
  重复创建任务。依赖：PC-009、PC-010。

### 8.3 等待状态和调度

- [x] **PC-012：增加等待状态和持久化字段。**
  为 `WAITING_PRECONDITION` 定义允许进入及离开的状态、等待记录、原因和审批引用，
  更新类型、持久化校验和所有状态消费者。新字段不得改变旧合同的授权含义。
  验收：旧队列数据可读取；新等待记录可重载；未知或损坏字段不能被默认为可执行。
  依赖：PC-001、PC-002。

- [x] **PC-013：在调度预留执行槽前检查。**
  在 reserve/dispatch 路径使用统一评估器；共享目录检查尽量复用，避免逐项重复
  全仓库扫描。耗时读取放在合适的锁范围之外，写入决定前核对所依据的状态。
  验收：条件不满足时不启动 Worker、模型或 Gradle，记录等待原因；没有其他任务
  能绕过同一共享目录限制。依赖：PC-006、PC-012。

- [x] **PC-014：在 Worker 创建工作区前补上竞态复查。**
  在 `src/queue/executor.ts` 的 prepare 阶段重新确认条件，处理调度检查完成后
  到实际启动前发生的文件变化；先检查，再执行分支、工作区及合同落地操作。
  验收：该时间窗口注入外部改动后进入可解释的等待，而非空原因 BLOCKED。
  依赖：PC-013。

- [x] **PC-015：明确等待时的执行槽与资源收尾。**
  覆盖“尚未启动 Worker”和“Worker 已启动但未创建工作区”两条路径，安全释放
  自己持有的执行槽和临时所有权，保留检查证据；不释放他人资源。
  若已发生部分工作区创建，则按原有恢复流程处理，不能谎报为尚未启动。
  验收：等待项不长期占槽，不消耗编码或修复预算，没有遗留活动 Worker。
  依赖：PC-014。

- [x] **PC-016：实现条件恢复后的复查调度。**
  使用既有事件唤醒和有界扫描检查等待项；同一条件不反复写盘或刷通知，不依赖
  模型轮询。必要时重新进入调度，但保持优先级、依赖与单执行槽约束。
  验收：移除外部改动后只启动一次，持续等待时没有模型调用或无界日志增长。
  依赖：PC-015。

- [x] **PC-017：落实基线变化与重新审批分流。**
  区分工作树恢复、已授权的前序集成、用户新提交和执行配置变化；能继续的严格
  沿用既有授权，不能继续的进入明确的重新规划/审批流程。
  验收：不会直接把旧合同 planningHead 改成新 HEAD，也不会自动缩小旧验证范围。
  依赖：PC-016、PC-011。

- [x] **PC-018：接通取消、暂停及维护操作。**
  等待且没有任务工作区的项目使用 cancel；保留 abort 对已有工作区的要求。
  检查 pause、resume、stop、依赖取消和重复请求对等待项的影响。
  验收：已取消任务不被重新唤醒；暂停时不开始普通任务；维护操作遵守既有授权。
  依赖：PC-012、PC-015、PC-016。

- [x] **PC-019：验证重启及生命周期兼容。**
  补齐服务重启后的等待重载、批准记录保持和重复启动防护；更新 lifecycle 对
  “等待且无工作区”与“仍占工作区”的区分。明确旧版本无法读取新状态时的行为。
  验收：重启不会重复批准或执行；升级不能越过活动任务；不通过删除旧状态恢复。
  依赖：PC-017、PC-018。

### 8.4 诊断信息与进程身份

- [x] **PC-020：修复空错误传播。**
  改进 Shell 干净工作区检查和 executor.helper 的失败信息；没有 stderr/stdout
  时仍包含检查名、退出码或信号。脏路径来自统一评估器，不暴露凭据或环境变量。
  验收：非零退出且输出为空的夹具产生明确错误，真实子进程错误也不被覆盖。
  依赖：PC-002、PC-006。

- [x] **PC-021：打通状态、通知和证据展示。**
  将等待原因、文件摘要、是否启动编码、是否占有工作区和下一步贯穿 status、
  review、CLI、通知及证据分页。按任务和实际条件变化去重，避免每次扫描都通知。
  验收：所有入口解释一致；大文件列表不挤掉审批问题；提交前缀不误入阻塞列表。
  依赖：PC-009、PC-012、PC-016、PC-020。

- [x] **PC-022：统一进程身份的区域设置。**
  梳理 storage、service、supervision 等使用进程启动时间的路径，统一新记录的
  采集格式；设计旧本地化身份记录的兼容处理，不能仅因格式不同就判定拥有者退出。
  无法证明身份时给出明确诊断，不能因此恢复锁、发信号或重复启动。
  验收：中英文环境交叉启动/查询一致，兼顾旧记录、PID 复用和僵尸进程场景。
  依赖：PC-001；可与其他阶段并行。

## 9. 执行顺序与完成标准

### 9.1 建议执行批次

| 批次 | 任务 | 批次完成条件 |
| --- | --- | --- |
| A：统一判定基础 | PC-001～PC-006、PC-023 | 共享只读检查可用，提交前缀例外及混合变更验证通过 |
| B：审批前阻止失效规划 | PC-007～PC-011 | 升级未提交不会生成可审批合同，审批与入队一致性成立 |
| C：执行前等待与恢复 | PC-012～PC-019 | 竞态后能等待、取消、重载，基线变化处理符合原授权 |
| D：可解释诊断与身份修正 | PC-020～PC-022 | 无空错误，各入口显示一致，跨 locale 不误判服务存活 |
| E：整体验证与交付准备 | PC-024～PC-030 | 集成、回归、包内验证和迁移文档均有证据 |

批次是建议排期，不覆盖每项列出的依赖。PC-010 可在检查模型确定后提前进行；
PC-012 可与审批接入并行；PC-020 可在统一评估器完成后提前修复；PC-022 可独立
开展。测试应随相应功能实施，而不是等最后一个批次才开始编写和运行。

### 9.2 每项完成时记录什么

每个任务勾选时，在完成记录中填写：任务编号、完成日期、变更文件、测试命令与
结果、证据位置，以及仍存在的限制。部分完成不勾选；依赖未满足时说明阻塞点。

总体完成必须同时满足：第 7 节验收场景覆盖、30 项任务的交付可追溯、没有未解释
的回归失败，并明确实际发布/升级是否发生。不得仅因状态枚举、提示文案或文档
已修改就宣布方案完成。
