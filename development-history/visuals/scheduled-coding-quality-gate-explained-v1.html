Reading Guide

先用三分钟读懂这版变化

如果只做决策，依次阅读“融合结论 → 总流程 → 技能边界 → 门禁 → 上线清单”。

00
What stays

保留原方案的外部控制

双 Job、显式状态机、Gradle 硬门禁、只读审查者、人工合并仍是安全主干。

What changes

补上模型内部工程纪律

编码 Job 只允许使用 TDD、有限调试和完成前验证；审查 Job 使用独立包装技能。

What is forbidden

无人值守时不开放交互型能力

头脑风暴、创建工作树、结束分支和并行子代理在 V1 中禁止自动触发。

Core Verdict

融合原则：内层纪律，外层裁决

Superpowers 能提高代理执行过程的严谨性，但不能成为通过门禁的唯一依据。

01
可以结合，而且适合结合；关键是不能把“代理说自己用了技能”当作质量证明。

Superpowers 负责“怎样思考与实现”；Scheduler 负责“何时运行”；脚本负责“客观证据”； 独立 Reviewer 负责“第二视角”；Human 负责“最终风险接受”。只有确定性门禁脚本有权将任务推进到 READY_FOR_REVIEW，编码代理无权自我认证。

Layer 1

人类批准

冻结需求、范围、非目标和验收条件。

Layer 2

技能纪律

TDD、系统化调试、完成前验证。

Layer 3

确定性门禁

测试、构建、Lint、范围与测试完整性。

Layer 4

独立裁决

只读 Reviewer 加人工合并，拒绝自审闭环。

Architecture

端到端融合流程

交互式规划只发生在人类在线阶段；定时阶段只执行已经批准、边界明确的原子任务。

02

图 1：Superpowers 只增强编码过程；状态推进仍由脚本、独立 Reviewer 和人类掌握。

边界说明：Superpowers 的 requesting-code-review 会倾向于在同一代理流程中派发审查子代理。 V1 只借用其审查思想，不把它当作独立审查的替代品；真正的 G7 必须来自另一个定时会话、只读权限和重新执行的证据。

技能白名单与禁用边界

V1 使用最小技能集。任何未在合同中明确允许的技能，都按拒绝处理。

Responsibility Split

四个角色，四种不可替代的责任

准确性来自权力分离：提出修改的人，不能同时决定修改已安全完成。

04

scheduled-coder 在白名单路径内按 TDD 修改，生成证据。 不得改规则、扩大范围、自写通过状态、推送或合并。 diff、测试记录、实现摘要

State Machine

状态机升级：把批准与阻塞显式化

状态只能由指定角色按规则转换；禁止用自然语言“看起来完成了”替代状态文件。

---
name: scheduled-quality-reviewer
description: Independently review one gated task without editing repository files.
---

1. Require state READY_FOR_REVIEW and load the approved contract.
2. Treat coder summaries as untrusted claims; inspect the actual diff and logs.
3. Re-run the required verification commands with fresh output.
4. Check acceptance criteria, regression risk, scope, test quality, and test weakening.
5. Do not edit code, tests, task contracts, state scripts, or evidence produced by coder.
6. Emit exactly one decision:
   - APPROVED with evidence and residual risks
   - CHANGES_REQUESTED with actionable findings
① 不信任摘要Reviewer 从 Git diff 和原始日志开始，而不是延续 Coder 的叙事。
② 新鲜证据借用完成前验证原则，关键命令在独立会话中重新运行。
③ 只读角色发现问题只给出结论，不顺手修复，避免审查与实现重新合并为同一权力。

Scheduled Jobs

两个 Job 的最小职责

调度器只负责触发与隔离，不在 Prompt 内实现状态机逻辑。

09
Job A

scheduled-coder

  • 只领取一个 PENDING 合同，并持有任务锁。
  • 显式调用 $scheduled-quality-coder。
  • 使用专用工作树，运行前必须干净。
  • 最长运行时间、文件数和修复循环均有限制。
  • 不 Push、不 Merge、不创建额外工作树。
Job B

scheduled-reviewer

  • 只领取一个 READY_FOR_REVIEW 合同。
  • 显式调用 $scheduled-quality-reviewer。
  • 只读仓库，证据目录另写审查报告。
  • 独立重跑关键命令，不接受 Coder 自述。
  • 通过后只推进到 AWAITING_HUMAN。
Prompt 建议：使用短 Prompt 指向项目包装技能和任务 ID，例如 Use $scheduled-quality-coder to execute exactly TASK-0001. Stop on any ambiguity. 详细规则应位于版本化 Skill、合同和脚本中，而不是散落在 Scheduler 的一大段自然语言里。

Integrity Controls

防止“测试绿了，但质量反而下降”

自动化最危险的失败不是命令报错，而是代理通过修改检查本身来获得绿色结果。

10
Test integrity

测试不可弱化

检查删除测试、加入忽略标记、放宽断言、吞异常、硬编码通过或只测实现细节。

Rule integrity

规则不可自改

对 Agent、Skill、任务合同、状态脚本和门禁脚本设置拒绝权限，并验证哈希或 diff。

Evidence integrity

证据不可替换

日志追加写、记录命令与退出码；Reviewer 重新运行关键命令以减少伪造价值。

测试修改策略：允许修改测试并不等于允许修改任何测试。合同应明确哪些测试文件可变； Reviewer 必须逐项解释测试变更为何增强行为约束。若任务本应只改实现，却出现已有测试被放宽，直接 CHANGES_REQUESTED。

Rollout Plan

分阶段落地，不一步跳到全自动

每一阶段只有在证据满足退出条件后才进入下一阶段。

12
  1. 阶段 A：手动接入
    安装并锁定 Superpowers；建立两个项目包装技能；在人工会话中验证技能选择、禁止项与权限拒绝。
  2. 阶段 B：脚本化门禁
    实现任务合同校验、状态原子转换、G0–G6、日志归档；先不接任何定时触发。
  3. 阶段 C：影子模式
    Scheduler 定时读取真实任务但不写产品代码，只演练领取、锁、预检和报告。
  4. 阶段 D：低风险试点
    选择 5–10 个小型、可回滚、无依赖升级任务；允许写代码，但仍不 Push、不 Merge。
  5. 阶段 E：评估扩展
    一周或一个试点批次后看指标，再决定是否扩大任务类型；V1 仍保留人工合并。

每阶段退出条件

  • 同一个任务不会被重复领取或并发写入。
  • Coder 无法修改 Agent、Skill、合同和门禁脚本。
  • 缺技能、脏工作树、需求歧义都会可靠进入 BLOCKED。
  • 测试失败不会被描述成成功，日志包含真实退出码。
  • Reviewer 在只读权限下可以独立重跑关键检查。
  • 任何状态都没有通往自动 Push 或自动 Merge 的路径。
首批任务优先选纯逻辑、本地单测覆盖、修改文件少且无设备依赖的工作；UI 大改、数据库迁移、权限、安全、支付和依赖升级不进入首批试点。

Evaluation

如何判断融合真的提高了准确性

不能只比较“测试是否通过”，还要衡量人类返工、越界、弱测试和漏出缺陷。

↑人工首轮验收通过率
↓Reviewer 阻断率（稳定后）
0越界修改与规则自改次数
0测试删除或弱化次数
↓合并后逃逸缺陷率
可解释歧义阻断率与原因
小而稳每任务平均修改文件数
100%成功结论附新鲜证据率
建议对照：用相似难度的小任务比较“原 Scheduler 方案”和“融合 V1”两个批次。 若融合后只是运行时间增加，却没有降低审查返工、范围违规或逃逸缺陷，就应缩减技能流程，而不是继续叠加更多代理仪式。

允许第一次真实定时写入前

14

配置与隔离

  • Superpowers 已安装并锁定可审计版本。
  • Coder/Reviewer 包装技能均能被显式发现。
  • 专用工作树已创建，运行前洁净检查有效。
  • Coder 写权限和 Reviewer 只读权限已用负向测试验证。
  • Cron 重叠时任务锁可以防止重复执行。

合同、门禁与恢复

  • C0、S0、G0–G7、H1 都有机器或人工责任人。
  • RED 证据、范围检查和测试完整性检查已实测。
  • 失败日志能定位到具体门禁和退出码。
  • BLOCKED 不会在下一周期自动重试。
  • 已完成至少一次成功演练和一次故意失败演练。
V1 的上线标准不是“代理能完成任务”，而是“代理犯错时系统能及时、确定地停下来”。

只要自动 Push、自动 Merge、规则自改或无限重试仍存在，就不应开启无人值守写入。
