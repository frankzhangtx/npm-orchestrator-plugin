ORCHESTRATOR · ARCHITECTURE PROPOSAL

自动执行 Agent
与任务队列解耦设计方案

用户持续规划、审批并插入合同，后台按队列串行执行。工作区默认复用固定工程目录，可选独立 Git worktree；固定目录下支持“人工确认后提交”（默认）与“全自动本地提交”。全自动只取消执行结束后的人工确认，不取消构建、全量单测和 Review。所有模式都禁止 git push。

01

先明确四个核心决策

交互与执行分离

确认入队后，前台立即返回

Planner 负责需求、计划和合同确认。长时间的编码与审查交给后台，用户随时可以继续提出下一项需求。

统一消费入口

定时与入队事件共用一个调度器

两种模式均保持每仓库一个执行名额，不并行启动多个 Coder。只消费当前模式允许运行的合同，无可运行任务时等待，不调用模型轮询。

工作区策略 · 默认不新增 worktree

复用目录为默认，独立工作区可选

固定目录等当前合同本地提交、集成及交接完成后再运行下一份。独立模式保留专属工作区，待验收时可让其他独立合同继续执行。

提交策略 · 不扩大远程权限

人工确认或全自动，只做本地提交

固定目录默认保留提交前人工确认；显式选择全自动后，通过同一质量门禁即可自动提交并本地集成。两者都禁止 git push，不能以测试通过代替提交授权。

预期使用体验：所有模式都允许在 A 执行期间继续确认 B、C 入队。固定目录的人工提交方式会等待 A 的最终确认；全自动提交方式不等待这次确认，但仍须等 A 本地集成完成才启动 B。独立 worktree 本轮保持人工提交，可在 A 待验收时执行独立 B。合同入队前的确认始终保留，远程推送始终禁止。

03

建议架构：前台生产，后台消费

Planner、队列和调度器共用；先按工作区策略确定目录，再按合同已授权的提交策略收尾。固定目录的两种提交路径详见第 07 节。以下均为拟实现流程，不表示当前插件已有异步队列或全自动提交能力。

04

拆分批准合同与开始执行

需求讨论→方案确认→合同复核→持久化入队→返回用户

入队成功后立即显示任务编号、排队状态、提交策略和等待原因。合同复核卡默认显示“执行后等待人工确认提交”；用户显式选择全自动时，须明确显示“通过质量门禁后自动本地提交并集成，不推送远程”。该选择随批准记录封存，轮到任务时无需再次确认是否启动，但不能将旧的人工提交授权当作自动提交授权。

拟拆出的职责

approve-and-enqueue

记录合同确认及明确选择的 commitPolicy，封存合同版本、工件哈希、目标本地分支和禁止推送约束，原子写入队列后返回。

拟拆出的职责

prepare-and-run

由调度器领取合同并固化工作区策略；默认占用固定目录，可选创建独立 worktree。复核基线与执行条件后，再运行单任务编排流程。

合同存放与代码读取

  • 两种模式的草稿和排队合同都存入独立收件区，例如 <git-common-dir>/automation-runtime/inbox/，不放在当前产品 diff 中。通过 Git 公共目录定位运行数据，兼容固定目录和多个 worktree。
  • 通过受控接口写入收件区，Planner 不需要任意修改 .git 的权限。审批记录与合同版本关联，普通草稿文件出现不等于获准执行。
  • 规划时固定目标分支上一个已提交的 planningHead，通过受控只读接口读取对应 Git 对象；不直接读取 Coder 正在编辑的文件，也不跟随活动目录的当前分支。Planner 不切分支、不修改产品代码，默认模式无需为规划额外创建 worktree。
  • 任务开始时，才将本任务的封存工件放入执行工作区的 docs/plans/ 与 automation/tasks/，不把其他排队合同带入任务 diff。
需要解耦的是入队，不是取消执行保护：Planner 的受控入队只使用短队列事务，不要求获得 Coder 持有的执行租约。原来的“两份规划文件”检查移到当前合同工件校验及准备阶段；其他合同留在收件区。默认模式继续独占产品目录，仍能允许新合同入队。以上入口与路径调整均为设计建议。
05

独立后台服务与统一触发规则

在插件包内增加后台调度服务，插件负责启停、状态和交互入口。后台进程与 Planner 会话分离，每个 Git 仓库只运行一个调度实例；前台关闭后，已启动的后台服务仍可工作。

首版沿用当前的 opencode run --agent … 启动方式。每份合同拥有独立执行记录和会话上下文，Reviewer 按现有流程启动新会话。后台常驻的是调度器，队列为空时不会让模型持续思考。

触发条件调度行为关键约束
新合同确认入队空闲时立即领取，忙碌时保留排队。完整持久化后才成为可领取任务。
定时到点扫描并领取符合条件的合同。与入队事件共用领取逻辑，不独立启动第二个 Coder。
执行退出、验收或集成结束按当前模式核对是否可以调度下一份。默认模式须完整结束并恢复可复用目录；独立模式可在进程退出且成果封存后让出名额。进程退出本身不是统一放行条件。
后台启动或恢复核对未结束的执行，再扫描遗漏任务。不能直接把所有运行中任务重置为待执行。
定期兜底扫描补偿遗漏的入队或完成通知。仍需满足批准、到期、依赖、执行名额和所选工作区策略的条件。

指定时间执行

例如“今晚执行”使用 notBefore，入队事件不会让任务提前启动。周期调度显式配置时区，建议默认 Asia/Shanghai。

睡眠与周期任务

机器睡眠期间无法执行。错过多个触发时间后默认合并为一次补偿检查。“每天生成新任务”使用单独确认的模板，每次生成新实例；模板授权须明确版本、范围及提交策略，定时触发本身不授予自动提交或推送权限。

OpenCode 官方提供适合脚本和自动化调用的非交互 run。新后台行为仍需在插件声明的目标 OpenCode 版本上验证。参考：OpenCode CLI · run。

06

双工作区模式、占用规则与构建成本

工作区默认使用 inPlaceExclusive，保留可选 isolatedWorktree。工作区策略回答“在哪里执行”，第 07 节的提交策略回答“是否等待最终人工确认”。两种工作区都串行执行 Coder，独立模式不是并行编程开关；本轮只为固定目录增加全自动提交。

比较项默认 · inPlaceExclusive可选 · isolatedWorktree
产品代码目录复用同一个固定工程目录，不新增 worktree。领取合同后，创建该合同的独立 Git worktree。
任务分支与会话仍创建独立任务分支，在固定目录切换；每份合同新建执行会话和记录。独立任务分支对应独立目录；每份合同新建执行会话和记录。
同合同内部复用基线、Coder、构建、单测、Reviewer 和返工使用同一目录。同一合同的这些阶段复用同一个 worktree，不按 Agent 或验证次数反复创建。
通过 Review 后人工提交方式保留占用、等待确认；全自动方式保留占用，直接进入受控本地提交与集成，不经过正常人工等待。本轮保持人工提交。A 安全封存且进程退出后释放名额、保留目录；独立 B 可以启动。
用户创建 B、C始终可以规划并确认入队，不修改 A 的活动目录。同样可以持续入队；入队本身不创建工作区。
下一份正常启动点A 满足所选提交策略，完成本地 commit、集成验证和目标分支更新，目录通过交接检查后；不是 Coder 退出或 commit 创建后立即交接。A 安全封存且名额空闲后；依赖 A 的合同仍须等 A 成为 COMPLETED。
构建与磁盘可跨合同保留目录内增量状态及构建产物，避免按合同复制目录。首次构建缺少本目录产物；可利用全局缓存，但每个工作区仍可能产生自己的构建输出。
适用取舍优先节省空间并复用构建状态；可选人工确认把关，或经预先授权全自动本地收尾。需要在等待验收时继续处理独立合同，接受多份成果的空间及集成管理成本。

配置与模式切换

已有配置字段以下仅为配置片段，不是完整配置文件
{
  "workspaceStrategy": "inPlaceExclusive"
}

默认值与当前插件模板一致。用户显式选择独立模式时，将值设为 isolatedWorktree；这两个值已有 schema 支持，本文提出的是它们接入新队列后的行为。

  • 首版工作区采用仓库级模式，不增加逐合同混用工作区策略。未领取合同按领取时生效的仓库配置执行，并固化 workspaceStrategy、taskRoot、taskBranch 与执行基线；提交策略则以批准时已封存的选择为准。
  • 切换模式前暂停领取，确认没有运行、待验收或仍待恢复且占用工作区的合同，并检查目标目录可安全交接。已有待验收成果不得因切换被覆盖、删除或重新解释。
  • 运行和恢复均使用该任务已固化的模式，不因配置文件后来变化而热切换目录。未开始的队列项及其批准记录保留。
  • 若切换后的工作区模式与排队合同已授权的提交策略不兼容，例如 isolatedWorktree + autoCommit，拒绝领取该合同并展示原因，等待用户调整并重新确认；不得静默改策略或扩大自动提交范围。

默认模式的目录交接

  1. 领取前确认固定目录无其他任务占用，无非预期的已跟踪或未跟踪改动；用户文件和既有受控允许项不得自动清除。
  2. 以复核后的目标分支提交创建任务分支，在原目录切换，再仅放入本合同的封存计划与合同。Planner 和其他合同不得切分支或写入产品文件。
  3. 按提交策略取得最终人工确认或校验预先授予的自动提交授权，再由受控提交器执行本地 commit。集成验证和目标本地分支更新完成后，确认目录可交接，才释放占用；任何方式都不执行 git push。
  4. 失败或人工中止不是自动清场信号。修复后完成，或经明确授权的中止流程封存成果并恢复可复用目录后，才允许下一份进入；禁止为消费队列自动丢弃修改。

锁与持久化占用分开管理

锁或占用记录规则模式差异
队列短锁入队、排序和原子领取只持有短事务，不等待模型或人工操作。两种模式共用；新合同入队不要求获取当前任务的执行租约。
执行名额每仓库一个，覆盖 Coder、Reviewer、有限返工、提交和实际构建验证。后台统一仲裁恢复及集成验证。固定目录的人工方式等待确认时保留名额；全自动方式持有名额直到本地集成完成。独立模式安全封存后可以释放。
工作区归属持久记录目录及所属合同，进程退出不自动抹去归属。默认模式保护唯一固定目录，直到完成或安全中止；独立模式持续保护各自封存目录，不阻止创建另一份目录。
Git 操作锁短暂保护创建分支、创建或移除 worktree、最终更新目标分支等操作；不持有它等待人工或长时间测试。两种模式都执行。默认模式还必须持有固定目录归属，防止其他操作切换活动分支。
进程结束 ≠ commit 已创建 ≠ 合同完成：固定目录的人工方式在 AWAITING_HUMAN 保留占用，全自动方式在提交和本地集成期间保留占用，两者均不阻止新合同入队。独立模式安全封存后可让出名额，但恢复、重新验证或集成验证必须重新申请名额，与其他合同串行处理。

构建及全量单元测试：两种模式保持同一质量门槛

每份合同仍须完成构建和全量单元测试，不因工作区或提交方式而省略质量验证。现有 claim-task.sh 在启用单测时先捕获全量基线，verify-task.sh 再执行配置的测试与构建，没有默认执行 clean；因此同合同最终验证可以利用前面阶段产生的构建状态。

默认模式：保留增量状态

合同交接时不默认删除 build/ 或项目级 .gradle/。由构建工具判断哪些任务需要重做；代码、依赖或构建配置变化仍可能造成缓存失效，不承诺每份合同都同样快。

独立模式：控制首次成本

新 worktree 的首次构建没有原目录的产物。使用相同 Gradle User Home 并启用构建缓存时，可复用匹配的任务输出；不同 worktree 不共享可写的 build/ 或项目级 .gradle/。参见 Gradle 构建缓存。

“全量”按实际执行测试验收：覆盖项目配置的所有单测模块与变体，并要求实际的 Test 任务在本次验收重新执行，不能只把 UP-TO-DATE 或 FROM-CACHE 当作本次全量实跑。针对这些测试任务禁用本次跳过和测试结果缓存，编译仍可复用缓存；不默认给整条命令加 --rerun-tasks，因为它连依赖任务也会重跑。此策略需在后续实现中落地并验证，不声称当前脚本已强制实跑。参见 Gradle 重跑规则。

独立模式需为保留的待验收及失败现场设置数量、磁盘上限，达到上限暂停领取但仍允许入队。两种模式都串行安排构建验证。此前约 2 秒的工作区测量仅指检出成本，不包含首次构建、全量单测或 Agent 启动，不能当作每份合同的完整运行开销。

07

固定目录的两种提交方式：都禁止推送

默认继续使用人工确认后提交，另提供显式启用的全自动本地提交。这里的“全自动”指合同已确认入队之后，从执行到本地提交、集成及调度下一份无需再次人工确认；不是取消需求 / 合同批准，也不是允许 Coder 自由执行 Git 写操作。

工作区策略提交策略（建议字段）最后是否等待人工远程推送
inPlaceExclusive · 默认humanApproval · 默认是。用户确认当前封存成果后，才允许本地 git commit。禁止 git push。
inPlaceExclusiveautoCommit · 显式选择否。批准时已授权自动本地提交，质量门禁通过后由受控提交器执行。同样禁止 git push。

本轮不扩展 isolatedWorktree + autoCommit 组合；配置与领取校验应明确拒绝该组合，不能把“固定目录支持全自动”推断为所有工作区策略都自动提交。

批准、提交与本地集成的边界

  1. 批准时封存提交策略：仓库级 commitPolicy 只是新合同复核卡的默认选项。用户确认的合同版本、工件哈希、目标本地分支、范围、提交策略及禁止推送约束一起封存。改变默认值不改变已入队或执行中的合同；把人工方式改成全自动，必须重新取得明确授权。
  2. 两条路径使用同一质量门禁：构建成功、全量单测实际执行并通过、Reviewer 为 APPROVED，且合同范围、保护路径、当前 diff 与最新封存证据一致。Coder 自述完成或某次旧测试通过都不够。
  3. 人工方式先确认，再 commit：进入 AWAITING_HUMAN，展示封存成果并等待用户确认。确认前不得创建任务成果 commit；确认必须匹配当前合同、diff 和基线，不能使用过期验收。
  4. 全自动方式验证授权，不伪造确认：新增自动提交策略校验入口，验证该合同已封存且未撤回的自动提交授权。通过后进入建议状态 READY_TO_COMMIT，无需生成一次虚构的人工验收，也不能把确认口令硬编码后调用现有人工入口来绕过检查。
  5. 受控提交器负责本地写入：两条授权路径共用经过验证的本地提交 / 集成核心，仅提交本合同允许的产品改动及规划工件，不混入用户文件。保持 Coder、Reviewer 无任意 commit / merge / push 权限，记录提交前基线、候选哈希、授权来源和 commit SHA。
  6. 本地集成完成才交接：延续现有收尾语义，在任务分支创建本地 commit，完成集成验证后更新记录的本地目标分支并恢复可复用目录。只有这一步成功才标记 COMPLETED；仅 commit 成功但集成失败不能启动下一份。

后续实现需要拆出“人工验收授权”和“自动提交策略授权”两种入口，再复用本地提交 / 集成核心；不可直接删除 automation_require_approval，也不可为自动流程伪造 acceptance.json。自动审计应记录真实的策略授权来源。

禁止推送是硬约束，不是可选设置

  • 配置与入口：pushAfterAcceptance 在所有组合中固定为 false。发现启用推送的配置或请求立即拒绝；启动、提交、集成、恢复和重试入口都校验，不能因为开启全自动就增加 push 开关。
  • 权限与受控执行：Planner、Coder、Reviewer、调度器和提交器都不得推送远程分支或标签，包括 --force、--force-with-lease、GUI 同步、别名或脚本间接推送。提交运行器须限制能绕过边界的 Git hooks、远程同步脚本或托管平台写入入口，不能仅依赖匹配一条字面的 git push 命令。
  • 本地操作边界：允许受控的本地 commit、验证及本地目标分支更新；不修改远程引用，不为实现禁推送而删除用户的 remote 配置。本次方案不提供任何“提交并推送”或出错后自动推送的路径。
  • 审计与验证：报告记录 commitPolicy、授权来源、候选 / commit SHA、本地集成结果和 pushed: false。该字段不能代替验证：后续测试使用隔离的本地仓库及命令替身，验证直接 / 间接推送被拒绝、模拟远程引用不变，不对真实远程发送写请求。成功、失败和恢复路径均需检查。
全自动失败时停止，不自动扩大权限：测试失败、Review 未批准、diff 漂移、授权失效、分支漂移或 Git 异常均保留现场并阻断收尾。已创建 commit 但尚未完成本地集成时，保留候选和占用，恢复时核对事务状态以避免重复 commit；不能自动推送、强制覆盖或直接领取下一份。
08

任务状态、队列记录与领取规则

两种工作区策略共用状态机；增加 QUEUED 表示已批准入队，并为全自动本地提交增加建议状态 READY_TO_COMMIT。Review 通过后，由受控编排器读取封存的 commitPolicy 决定分支，不由 Coder 自己宣布可以提交。

建议状态主路径为便于阅读省略批准记录与已有的有限返工分支
CONTRACT_REVIEW
    → QUEUED（拟新增：已批准入队，尚未占用执行目录）
    → PREPARING（按策略准备目录）→ PENDING → CODING
    → READY_FOR_REVIEW → REVIEWING

人工提交 humanApproval：
    REVIEWING（APPROVED）→ AWAITING_HUMAN
    → 人工确认当前封存成果 → INTEGRATING → COMPLETED

全自动提交 autoCommit（仅固定目录）：
    REVIEWING（APPROVED）＋ 自动提交授权有效
    → READY_TO_COMMIT（拟新增）→ INTEGRATING → COMPLETED

INTEGRATING：本地 commit → 集成验证 → 更新本地目标分支
任一路径失败：返工或阻断；不推送、不提前交接

QUEUED

合同已确认入队，提交策略已封存，但尚未占用执行目录。固定目录可因上一份待确认、提交、集成或待恢复而等待；独立模式还需考虑容量。两者都检查名额、时间和依赖。

PENDING

沿用现有含义：执行工作区已准备好，等待 Coder 接手。不能直接把所有排队合同都当成这个状态。

READY_TO_COMMIT

建议仅用于全自动方式：质量证据及策略授权已核验，等待受控本地提交。它不表示人工已验收，也不表示 commit 或本地集成已完成。

建议的最小队列及关联运行记录

字段分组记录内容作用
合同身份与封存合同 ID、版本、合同与计划哈希、对应批准记录。绑定用户确认的准确内容，防止排队期间被替换。
提交策略与授权批准时封存的 commitPolicy、策略版本、授权记录引用、目标本地分支及禁止推送约束。区分执行后人工确认和预先授权全自动提交。策略变更需重新确认，不能只读取当前配置来扩大旧合同权限。
排序与时间入队顺序、优先级、最早执行时间 notBefore。决定可领取的时间与顺序。
分支与依赖目标分支、planningHead、执行基线、dependsOn。确定代码版本与前置任务是否满足。
工作区身份领取后固化 workspaceStrategy、sourceRoot、taskRoot、taskBranch 和占用者。默认模式 taskRoot = sourceRoot；独立模式使用不同目录。恢复时禁止重新套用后来修改的模式配置。
执行与恢复当前状态、runId、尝试次数、等待原因及进程归属信息。支持审计、状态显示和中断恢复。
本地提交事务提交事务 ID、提交前 HEAD、封存 diff、候选 / commit SHA、目标分支更新结果、真实授权来源及 pushed: false。区分未提交、已提交未集成和已完成，支持幂等恢复；自动授权不伪装成人工验收记录。

统一领取规则

  1. 只考虑已确认入队、到达执行时间、依赖已完成的合同；检查提交授权有效，且工作区与提交策略组合受支持，禁止推送约束未被改变。
  2. 确认执行名额允许领取，且没有公共故障、暂停或归属不明的运行进程。默认模式还要求上一份完整结束或安全中止、固定目录可复用；独立模式要求未达到工作区容量上限。
  3. 默认按入队顺序消费，可支持优先级调整；不抢占正在执行的合同。
  4. 在短事务中领取并记录本次 runId 与工作区策略。复核规划基线和合同适用性后，再按模式占用固定目录或创建独立 worktree，准备本合同工件并启动执行。

等待原因与任务状态分开显示，例如“等待 A 人工确认”“等待 A 本地集成”“提交授权需重新确认”“等待固定目录恢复”“等待依赖 A 完成”或“隔离工作区容量已满”。全自动的正常路径不显示虚构的“人工已验收”。

合同版本不可被悄悄替换：同一合同版本重复提交返回已有队列项。已批准内容需要修改时，生成新版本并重新确认；正在执行的版本保持封存。失败任务、人工待办和队列等待原因应清晰区分。

提交、任务依赖与基线变化

所有受支持组合都以 COMPLETED 作为依赖完成标准，即成果已经验证并集成到本地目标分支，不以推送远程为条件。人工提交等待最终确认，全自动提交不等待；固定目录的两种方式都必须等当前合同本地收尾完成，独立 worktree 才能在待验收时先执行其他独立合同。通过 Reviewer 或仅创建 commit 都不等于依赖完成。

下面的 A / B / C 表展示 humanApproval 情况。固定目录采用 autoCommit 时，A 不进入正常人工等待，而是自动提交并本地集成；B、C 仍须等待 A 完成后再按各自条件领取。

任务与前提默认 · inPlaceExclusive可选 · isolatedWorktree
A：已通过 Review，等待人工验收继续占用固定目录与逻辑执行名额。进程可以退出，队列暂不领取下一份。确认进程退出且安全封存后，让出名额；A 的独立目录继续保留。
B：已入队，与 A 独立等待 A 验收并集成，或完成获授权的安全中止。正常完成后，B 在同一目录的新任务分支执行。名额空闲且容量允许时，可在自己的 worktree 执行，代码基线不包含 A 的未合入成果。
C：已入队，dependsOn = [A]等待 A 成为 COMPLETED，再按队列规则领取。同样等待 A 成为 COMPLETED；不能仅因 A 通过 Review 就启动。

规划基线与执行基线，不能混为一谈

默认模式下，B 可能在 A 编码期间已经完成规划；即使等 A 合入后才执行 B，也必须先复核旧 planningHead 对应的合同是否仍适用。独立模式还会遇到 B 已经执行完、但 A 随后合入的情况，此时 B 的集成候选需要重新验证。

当前集成脚本要求目标分支停在记录的执行基线。默认路径可保留现有漂移阻断；独立模式的待验收持续消费能力需要补齐受控的新候选验证流程，不能直接删除检查或把原有 block 策略改成无条件合入。

开始执行前 · 两种模式比较 planningHead 与当前目标分支，复核合同前置条件、相关代码及测试，记录本次执行基线。需要修改合同或无法确认适用性时，暂停该合同并等待重新规划、重新确认，保留原版本与批准记录。
准备集成时 · 按策略默认模式保留漂移阻断并转受控处理；独立模式若目标分支已前进，按受控流程生成最新基线上的候选，重新构建、全量单测、Review 和封存。冲突或超出合同范围时保留现场。不得复用旧测试结论，也不得静默修改合同内容。
提交授权核验时人工方式将确认绑定到合同、候选与目标基线，候选变化后重新确认；全自动方式核验封存的策略授权及当前质量证据，不生成最终人工确认。旧证据不能用于新候选；授权撤回、合同变化或固定目录分支漂移时阻断，不因全自动而绕过。
最终更新分支时短暂持有集成锁，再次核对目标 HEAD。验证期间又发生变化，则重新处理。不让未经验证的新组合进入目标分支。
独立模式的额外要求：工作区隔离解决多份待验收成果共存，基线重新验证解决它们先后合入。A 发起验收时若 B 仍在执行，A 的集成验证须等待同一个执行名额，不并发启动第二组构建；最终验收绑定最新封存候选，候选变化必须重新确认。默认模式在 A 完成前不会启动 B，因此没有这种内部交错，但仍需执行前基线复核和最终分支校验。

持久化、异常恢复与用户操作

首版可沿用现有 JSON 状态文件和审计记录。触发事件负责唤醒，持久化状态负责决定任务能否执行；事件重复或丢失都不应改变这一原则。

场景处理规则
合同写入尚未完成合同与计划完整持久化后，队列项才变为可领取。状态更新使用短锁和原子替换。
定时与入队事件同时到达通过统一的原子领取操作，只产生一个有效 runId；其他唤醒重新读取状态。
入队成功，通知丢失启动扫描与兜底扫描发现任务，按同样条件领取。
调度器重启或心跳超时先核实原执行进程是否仍存活。不能只因超时就启动第二个 Coder；无法确认归属时保留现场并等待恢复处理。
单份合同失败 · 默认模式保留固定目录占用和失败现场，停止领取下一份但继续接收入队。等待修复后完成，或经明确授权中止、封存并恢复可复用目录；不能只凭进程退出释放占用。
单份合同失败 · 独立模式只有确认进程退出、失败状态与成果安全封存、目录归属明确且非公共故障时，才可让出名额并检查其他独立合同。失败不等于待验收或依赖完成；重试须重新申请执行名额。
重启后发现固定目录脏或模式被改按原运行记录核对目录、分支、基线及所属合同；保留现场并阻断不安全交接。不得使用新的配置覆盖旧任务模式，也不得自动 reset、clean 或删除用户修改来启动下一份。
全自动提交授权异常授权缺失、被撤回、合同哈希或策略被篡改时，停止自动收尾并展示原因。不伪造人工确认、不自动改变策略，也不启动下一份占用该目录的合同。
commit 已创建但本地集成失败保留候选 commit、证据及固定目录占用，记录 INTEGRATION_BLOCKED 或对应阻断状态。不报告 COMPLETED，不推送远程，也不盲目再次 commit。
提交或集成时崩溃按提交前写入的事务意图、任务分支历史、候选树和本地目标引用核对。若已创建正确 commit 则复用；若已完成目标更新则核验后补记状态；无法证明一致时保留现场，不重复提交或强制覆盖。
任何直接或间接推送请求在人工、全自动、失败恢复和重试路径中都拒绝。错误信息及完成通知只报告本地状态，不提供“推送以完成任务”的操作。
公共环境或认证故障暂停队列消费，显示公共故障原因，避免让每个排队任务重复失败。
用户暂停或取消暂停停止领取新任务，当前任务继续到安全结束点。取消运行中任务走有记录的中止流程。

建议的用户入口

队列与任务详情

分别展示工作区策略和提交策略、授权来源、目录、分支、占用者及依赖。区分“等待人工确认”“自动提交中”“本地集成中”和“已完成 · 未推送”，成功后显示本地 commit SHA，不混淆提交与推送。

暂停、恢复与策略调整

允许暂停、恢复、排序、取消以及进入受控恢复流程。工作区切换遵守第 06 节；提交策略遵守第 07 节的重新授权规则，不能用全局配置改动把待人工确认的合同直接自动提交。

按提交方式提供持久化通知：人工方式展示与最新封存成果绑定的验收待办；全自动方式展示“已自动本地提交并集成 · 未推送”及 commit SHA，失败时展示阻断原因而非假定人工已验收。通知不依赖原 Planner 会话持续等待，任何通知入口都不能触发远程推送。
11

实施顺序与验收清单

按三个阶段推进：先完成入队及策略授权封存，再完成固定目录下人工 / 全自动本地提交的串行闭环，最后补齐独立 worktree 的待验收持续消费。工作区默认 inPlaceExclusive，提交默认 humanApproval；所有阶段禁止推送远程。

阶段 1 · 持续入队与授权

拆分生产与执行

增加收件区及队列，拆分审批与执行入口，调整 Planner 读取路径；在合同复核时明确并封存提交策略和禁止推送约束。

验收结果：A 执行时可确认 B、C，不污染 A 的 diff；旧合同不因默认配置变化获得自动提交权限。

阶段 2 · 固定目录两种提交

人工确认 / 全自动本地收尾

接入调度与目录交接，拆出两种授权入口及共用提交核心，落实全量单测实跑、提交事务恢复和各路径禁推送。

验收结果：人工方式确认前不 commit；全自动方式门禁通过后自动 commit 并本地集成，随后启动 B。失败保留占用，两者都不 push。

阶段 3 · 可选独立模式闭环

封存成果与串行集成

接入独立 worktree，完成封存后的名额释放、容量限制、依赖与候选重新验证，以及模式切换保护和双模式回归。

验收结果：显式选择独立模式后，A 待验收时独立 B 可执行，依赖 A 的 C 等 A 合入；默认行为不改变。

未来实现的验收要求

以下是开发完成后应验证的场景，不表示本次已经实现或运行通过。

  • 01默认配置保持兼容：默认 inPlaceExclusive + humanApproval，任务根目录等于源目录；仍创建任务分支，完成后恢复本地目标分支，旧合同不自动获得提交权限。
  • 02可选独立模式有效：显式选择 isolatedWorktree 后，仅在领取时创建独立目录；同合同的 Coder、Reviewer 和返工复用该目录。
  • 03两种模式持续入队：A 执行或待验收时创建并确认 B、C，前台及时返回；Planner 读取固定提交，不污染 A 的文件和 diff。
  • 04固定目录完整串行：A 等待人工确认、自动提交中、集成中或失败待修复时，B 不能启动；本地完成或安全中止并通过交接检查后才放行。
  • 05独立模式验收分离：A 安全封存且进程退出后，独立 B 可执行；依赖 A 的 C 必须等 A 合入。
  • 06始终只有一个执行名额：不并行运行两个 Coder；独立模式的恢复、重新验证和集成构建，也不得绕过正在被 B 使用的名额。
  • 07多任务排序与去重：多份合同按规则领取；定时、入队和完成事件并发时，同一合同只产生一个有效执行实例。
  • 08计划时间有效：尚未到 notBefore 的合同，不因入队通知或兜底扫描而提前运行。
  • 09前后台与恢复可靠：关闭前台不停止已启动的后台；重启先核对进程、目录归属和状态，无法确认时不重复启动 Coder。
  • 10基线与批准准确：领取前复核基线，候选变化重新验证；人工方式重新取得匹配确认，全自动方式核验策略授权且不绕过漂移阻断，合同变化重新确认。
  • 11模式切换安全：活动、待验收或待恢复合同占用现场时拒绝切换；安全切换保留队列，恢复始终使用任务固化的模式。
  • 12失败和用户修改不丢失：默认目录脏时阻止交接；独立模式仅在安全封存后继续消费，不为启动下一份而自动丢弃任何现场。
  • 13全量单测实际执行：两种模式都执行构建和覆盖全部配置模块、变体的单测，报告可证明实际测试已重跑，而非仅恢复旧测试结果。
  • 14构建状态按模式复用：默认目录交接不默认 clean；独立目录不共享可写构建输出。分别记录首次验证与后续验证耗时，不将创建目录耗时当作构建耗时。
  • 15内容与通知持久：未写完或未经批准的合同不可执行；通知丢失由扫描补偿，待验收通知与最新封存结果绑定。
  • 16控制与资源约束有效：暂停停止领取；公共故障、独立工作区容量超限可暂停消费，同时允许入队并保留失败现场。
  • 17人工确认前不 commit：质量门禁通过后仍等待用户；未确认、确认过期或不匹配当前 diff 时不创建任务成果 commit。
  • 18全自动无需最终确认：固定目录下已明确授权 autoCommit 的合同通过门禁后，无最终人工问题即可本地 commit、验证并集成，随后执行下一份。
  • 19全自动不降低质量：构建、全量单测或 Review 任一失败，以及 diff 漂移、授权撤回、分支异常时，均停止自动提交，不伪造人工验收。
  • 20授权不随默认值升级：把仓库默认改成全自动，不改变已入队或待人工确认合同；显式重新授权后才允许修改提交策略。
  • 21禁止所有远程推送：人工、全自动、失败及恢复路径均不调用远程推送；直接 / 间接推送、force、标签与同步入口被拒绝，验证远程引用不变。
  • 22提交事务可恢复：分别在 commit 前后、集成验证中、目标分支更新后中断；恢复不重复 commit、不强制覆盖，不在本地集成完成前交接。
  • 23组合范围受控：拒绝本轮未支持的 isolatedWorktree + autoCommit；工作区切换与排队合同策略不兼容时明确阻断，不静默降级或扩大权限。
  • 24完成报告真实：人工与全自动分别记录真实授权来源；展示本地 commit SHA、集成结果和“未推送”，不把自动决策标成人工已验收。
交付边界：阶段 2 完成固定目录的人工 / 全自动本地提交闭环；阶段 3 完成独立 worktree 的人工验收持续消费。最终默认仍为固定目录、人工确认提交。全自动是已批准合同的本地收尾能力，不是远程推送能力，所有组合都保持禁止 git push。
