OpenCode Scheduler × Android Quality Gate

定时编程、单测验收与独立大模型评审方案

面向当前 cctest Android 工程的可落地自动化设计：让 Scheduler 只负责可靠触发， 让确定性的 Gradle 测试承担验收，让第二个只读模型承担代码评审，最后由人决定是否合入。

目标工程：/Users/zhanglong/files/program/cctest
已安装：opencode-scheduler 1.3.0
平台：macOS / launchd
文档类型：实施方案，不修改应用源码
推荐结论：双任务、双角色、三道硬门禁、人工合入

不让编码模型自己宣布“完成”。编码作业只生成候选改动；单元测试与构建命令根据退出码裁决； 独立评审作业复查需求、差异和测试质量。任何失败都停止推进，绝不自动推送、合并或发布。

阅读抓手

先抓住这五条原则，再看后面的目录、配置和提示词模板。

01

任务必须可验收

每个任务都写清允许修改范围、禁止项和可执行的验收命令；没有验收标准就不领取。

02

隔离工作区

使用专门的 Git worktree，避免夜间任务覆盖你白天尚未提交的改动。

03

测试退出码裁决

模型的文字总结不算通过；只有 Gradle 命令返回 0 且报告存在，才允许进入评审。

04

评审角色只读

评审模型不能修改业务代码，只能读差异、重跑测试并写结构化评审报告。

05

人工决定合入

第一阶段禁止自动 push、merge、发布和删除；通过评审也只进入待人工确认状态。

主执行流程图

两个 Scheduler 作业通过状态文件交接；任何失败都走“保留证据并停止”的支路。

菱形是硬判断，圆角矩形是可执行步骤，虚线代表两个独立 Scheduler 作业之间通过状态文件交接。 插件只能保证同一个作业不重入，因此方案还要求使用共享的原子目录锁，防止编码作业与评审作业交叉修改状态。

三个角色的边界

准确性来自职责分离：模型负责推理，脚本负责裁决，人在最终风险点签字。

编码 Agent

每次最多领取一个任务；先读 AGENTS.md 和任务契约；先跑基线；实现最小变更并添加测试。 可编辑工程，但禁止 push、merge、发布、删除工作区以及修改测试以掩盖失败。

质量门禁脚本

使用固定命令和退出码，不接受自然语言“看起来通过”。保存命令、开始/结束时间、退出码、测试报告路径和 diff 摘要，失败立即停止。

独立 Reviewer

新会话、低温度、优先不同模型；业务代码只读。核对任务与 diff，重跑关键测试，寻找测试弱化、越界修改、隐患和遗漏，并输出结构化结论。

状态机与交接协议

状态是两个独立模型之间唯一可信的控制面；聊天文本不作为状态。

状态 谁可以进入 必备证据 下一步
PENDING 人工创建任务 任务 ID、目标、允许路径、验收命令 编码作业原子领取
CODING 编码作业 基准提交、worktree、开始时间、锁所有者 运行质量门禁
TEST_FAILED 门禁脚本 退出码、失败测试、日志、当前 diff 停止；等待人工或下一轮修复
READY_FOR_REVIEW 全部硬门禁通过后 diff 校验值、测试报告、构建与 lint 结果 评审作业领取
CHANGES_REQUESTED Reviewer 按严重级别排序的问题与可复现证据 返回修复或人工终止
AWAITING_HUMAN Reviewer 通过后 APPROVED 报告和全部门禁证据 人工查看、commit / merge 或拒绝
两个作业都先尝试用 mkdir 创建同一个锁目录。创建失败表示另一个流程仍在运行，当前作业只记录 SKIPPED_LOCKED 并退出；不要依赖两个 Cron 时间“应该不会撞车”。

质量门禁矩阵

“硬门禁”失败立即终止；条件门禁必须明确记录是否具备运行环境。

门禁 命令 / 检查 类型 通过标准
G0 基线 ./gradlew testDebugUnitTest（编码前） 硬门禁 退出码 0；当前已失败，所以暂不具备启用条件。
G1 任务测试 针对本次功能新增或修改的 JUnit4 / Espresso 测试 硬门禁 测试真正覆盖任务验收条件；不得只有“能编译”或恒真断言。
G2 全量单测 ./gradlew testDebugUnitTest（编码后） 硬门禁 全部通过，不允许删除测试、加 @Ignore 或弱化断言换绿。
G3 构建 ./gradlew assembleDebug 硬门禁 退出码 0，生成可安装的 Debug APK。
G4 静态检查 ./gradlew lint 硬门禁 退出码 0；新增问题不能通过改配置隐藏。
G5 设备验收 ./gradlew connectedDebugAndroidTest 条件门禁 有受管模拟器时全绿；没有设备时明确记为 NOT_RUN，不能写 PASS。
G6 模型评审 独立 Reviewer + 必要测试复跑 硬门禁 没有 Blocker / High 问题，测试未被削弱，改动未超范围。

# Reviewer 与 Coder 的目标不同：主动找出拒绝合入的理由。
你是独立代码评审者。不得修改业务源码、测试源码、构建配置或候选 diff。

核对任务契约、基准提交、当前 diff 与质量门禁证据，并重点检查：
- 需求是否完整实现，是否有边界条件和回归风险；
- 是否删除、跳过、弱化测试，或只写了无法失败的测试；
- 是否修改了允许范围之外的文件；
- 是否引入线程、生命周期、资源、导航、安全或敏感信息问题；
- AGENTS.md 中的 Android / Kotlin 约定是否满足。

## 目标
说明用户可观察到的行为，不写“优化一下”这类不可验收描述。

## 验收标准
1. 合法手机号保持现有行为。
2. 非法手机号返回明确的校验错误。
3. 至少新增正常、边界、异常三类单元测试。
4. ./gradlew testDebugUnitTest、assembleDebug、lint 全部通过。

## 非目标
- 不调整页面视觉样式。
- 不重构无关导航或网络模块。

## 人工评审关注点
- 是否误伤已有中文输入解析；
- 是否把用户文案硬编码进 Kotlin；
- 测试是否真的能在实现错误时失败。

分阶段落地顺序

不要一次性开放所有自动权限；每一阶段都有明确的退出条件。

P0

先修复基线

确认并修复当前失败的 ExampleUnitTest，连续两次运行全绿。梳理现有未提交改动，不让自动任务处理它们。

P1

建立隔离和骨架

创建专用 worktree、Agent、命令、任务模板、状态目录、原子锁和门禁脚本；配置最小权限。

P2

手工端到端演练

选择一个低风险任务，先“立即运行”编码作业，再运行 Reviewer；检查 diff、退出码、日志和状态跳转。

P3

开启夜间 Cron

先运行一周，每晚最多一个任务；保留人工合入。统计失败原因、误改范围、测试漏报和评审召回率。

P4

增强设备与覆盖率

配置固定模拟器后，把关键 Espresso 流程升级为硬门禁；再考虑 JaCoCo/Kover 覆盖率阈值。

P5

有限自动提交

稳定后可允许提交到专用本地分支，但仍禁止 push、merge、发布；任何外部写操作继续保留人工授权。

上线前检查清单

全部满足后，才值得让 macOS 在无人值守时自动执行代码变更。

  • 当前 testDebugUnitTest 基线已经修复并连续全绿。
  • Scheduler 使用独立、干净的 worktree，而不是当前有用户改动的目录。
  • 任务契约写明允许路径、禁止路径、验收条件和最大变更规模。
  • 编码 Agent 的 bash 权限采用白名单，显式禁止 push / merge / 删除。
  • 质量门禁脚本保存真实退出码和报告路径，失败立即停止。
  • Reviewer 是独立新会话，优先使用不同模型，业务源码没有写权限。
  • Reviewer 检查测试是否被删除、跳过、弱化或绕过。
  • 两个作业使用共享原子锁和明确状态，不只依赖 Cron 时间错开。
  • 手工 run_job 演练成功，并检查 Scheduler 日志与运行产物。
  • 通过评审后仍停在 AWAITING_HUMAN，没有自动合并或发布。
